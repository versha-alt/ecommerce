# CMS

## Assumptions

-   Admin-only scope. Storefront implementation is excluded; only admin
    configuration and explicit storefront contracts/impact are
    documented.
-   Single Kenyan retailer, multi-brand, omnichannel, English-first and
    Swahili-ready.
-   Currency is KES; prices are VAT-inclusive by default. VAT supports
    16%, zero-rated and exempt classes.
-   Scale baseline: 5--10K active SKUs at launch, 300--500 orders/day
    with 3--5× peaks; architecture must remain viable toward 100K+
    products and 1M+ customers.
-   API prefix is `/api/v1`; IDs are UUIDs; timestamps are UTC ISO-8601
    and rendered in `Africa/Nairobi`.
-   Backend is NestJS + TypeScript; PostgreSQL is system of record;
    Redis provides cache/queues; OpenSearch provides catalog/admin
    search and facets.
-   Admin frontend is React + TypeScript + Vite, TanStack React Query,
    React Hook Form + Zod, and MUI as the recommended component library.
-   Every mutation writes an immutable audit event containing actor,
    action, entity, before/after summary, IP, user agent and correlation
    ID.

## Purpose

Backend content management for pages, reusable blocks/widgets, homepage
composition, navigation/mega menu, store locator, services/enquiries,
blog, media, redirects and sitemap/robots.

``` ts
interface ContentPage { id:string; slug:string; title:string; status:'draft'|'scheduled'|'published'|'archived'; blocks:ContentBlock[]; seo:{title?:string;description?:string}; publishAt?:string; version:number }
interface ContentBlock { id:string; type:string; data:Record<string,unknown>; deviceVisibility?:('mobile'|'tablet'|'desktop')[] }
interface StoreLocation { id:string; name:string; city:string; address:string; lat?:number; lng?:number; phone?:string; hours:unknown; services:string[]; status:string }
```

``` sql
CREATE TABLE cms_pages(id uuid PRIMARY KEY,slug text UNIQUE NOT NULL,title text NOT NULL,status text NOT NULL,content jsonb NOT NULL,seo jsonb NOT NULL DEFAULT '{}',publish_at timestamptz,version int NOT NULL DEFAULT 1);
CREATE TABLE cms_versions(id uuid PRIMARY KEY,entity_type text NOT NULL,entity_id uuid NOT NULL,version int NOT NULL,payload jsonb NOT NULL,created_by uuid,created_at timestamptz DEFAULT now(),UNIQUE(entity_type,entity_id,version));
CREATE TABLE store_locations(id uuid PRIMARY KEY,name text NOT NULL,city text NOT NULL,address text NOT NULL,lat numeric,lng numeric,hours jsonb,services text[],status text NOT NULL);
CREATE TABLE url_redirects(id uuid PRIMARY KEY,source_path text UNIQUE NOT NULL,target_path text NOT NULL,status_code int NOT NULL CHECK(status_code IN (301,302)));
```

## Pages

Seed content types: About, Contact, Privacy, Terms, FAQ, Shipping &
Returns, Warranty. WYSIWYG/block editor, SEO, scheduling, preview and
immutable versions. Publish is permissioned.

## Blocks/widgets

Reusable content references are versioned. Updating a reusable block
shows impacted published placements before publish.

## Homepage builder

Ordered sections: hero, category grid, offers, rule-driven product
carousels, shop-by-brand, store locator and services. Each section
supports schedule and device visibility. Rule-driven carousels store
declarative rules, not product HTML.

## Navigation / mega menu

Header/footer trees plus mega-menu columns, category references, promo
tiles and brand logos. Broken/unpublished references block publish or
require explicit override.

## Store locator

CRUD for 7+ showrooms/warehouse public locations, hours, services,
contact, coordinates and status.

## Services / enquiries / WhatsApp

Service definitions and enquiry inbox with lead statuses
`new|contacted|qualified|won|lost`. WhatsApp click-to-chat config stores
approved destination/template parameters.

## Blog/media/URLs

Blog posts have author, category/tags, schedule and SEO. Media library
stores metadata/alt text and CDN rendition status. URL rewrites prevent
loops/chains where possible. Sitemap/robots editors validate syntax.

## REST admin

CRUD `/api/v1/cms/pages`, `/blocks`, `/homepage`, `/navigation`,
`/store-locations`, `/services`, `/enquiries`, `/blog/posts`, `/media`,
`/url-redirects`; publish/preview/version endpoints.

## Content-delivery API

Read-only, cacheable: - `GET /api/v1/content/pages/:slug` -
`GET /api/v1/content/homepage` -
`GET /api/v1/content/navigation/:code` -
`GET /api/v1/content/store-locations` Responses include
`contentVersion`, `publishedAt`, `etag`.

## Publish + ISR invalidation contract

On successful publish:

``` json
{"event":"cms.content.published","entityType":"page","entityId":"uuid","paths":["/about"],"contentVersion":12,"occurredAt":"2026-10-05T05:30:00Z"}
```

Storefront invalidation consumer revalidates exact paths/tags. CMS
records delivery status but publish remains successful if invalidation
is temporarily unavailable; retry queue handles delivery.

## Permissions

`cms.pages.read|manage|publish`, `cms.blocks.manage`,
`cms.homepage.manage|publish`, `cms.navigation.manage|publish`,
`cms.store_locator.manage`, `cms.blog.manage|publish`,
`cms.media.manage`, `cms.redirects.manage`.

## Edge cases

Slug collisions and redirect loops rejected. Scheduled publish uses UTC
storage. Deleting referenced media/block is blocked. Preview tokens are
short-lived and non-indexable.

## Audit

All publish/unpublish, version restore, navigation changes, redirects,
media deletion and enquiry status changes.

## Storefront impact

The storefront consumes only the content-delivery API and invalidation
events; it never queries CMS admin storage.

## Standard list/filter contract

List endpoints support `page`, `pageSize`, `sort`, `q` and
module-specific filters. Unknown filters return `400`. Exporting the
current filter creates an async job. Saved views are user-owned unless
explicitly shared by an administrator.

## Standard mutation response

``` json
{"data":{"id":"uuid","version":2},"meta":{"correlationId":"req_..."}}
```

Validation failures use HTTP 422; authorization uses 403; optimistic
version conflict uses 409; missing resource uses 404. External provider
failures map to stable internal error codes and retain provider
correlation IDs without leaking secrets.

## Observability

Every request carries a correlation ID. Metrics include latency/error
rate, queue lag and provider failure counts. Domain events use an outbox
transaction so database state and event publication cannot silently
diverge.
